# Codex voice coordinator for macOS: Caps Lock and voice allocation

Status: implementation plan only. Source baseline: `4bc83aa5f7ebfec8492bb5747affe0fc8433fcad`.

## Outcome and scope

Provide an optional headless Codex extension/helper for local macOS voice sessions: Caps Lock start/stop, a physical LED indicator and unique voice allocation across managed terminal instances, synchronized with native terminal lifecycle controls. A separate future menu bar app can consume the same interface and add independent microphone/playback mute and a count of completed voice messages received while playback is muted. Neither the helper nor the initial acceptance criteria requires that app.

The first release targets local macOS CLI processes, with a proposed minimum of macOS 13 subject to HID verification. It is an optional headless helper in this repository, launched on demand as a Rust binary or Codex subcommand, with no AppKit, SwiftUI, menu bar or GUI requirement. It does not capture audio itself, change the Mac's system volume, require an iOS app, or replace the terminal. Remote CLI sessions, general global keyboard shortcuts, automatic launch at login, App Store packaging, and task cancellation controls are outside this first implementation. Optional system-wide Caps Lock ownership is separately enabled and permission-gated.

This document proposes interfaces; it does not claim that a companion, control endpoint, or persistent speaker mute already exists. **Task A implements Caps Lock native voice lifecycle with global OFF and a confirmed aggregate LED; Task B implements a provider-specific round-robin pool of currently free voices. Both are in scope, and voice allocation does not depend on foreground detection.** ON targets the explicitly selected/bound instance through CLI registration/configuration; OFF stops every managed local voice session. Foreground routing is an optional feasibility investigation with explicit selection as its fallback. Richer menu/icon reuse, independent mute controls and unread counting remain deferred research, not initial acceptance requirements. This PR amends the plan only, without implementing either task.

## Extension-first decision and upstream maintenance

Prefer an optional external helper and existing APIs, with the smallest necessary core patch. “Extension” describes deployment here; the current plugin API does not supply the required native audio-owner hooks. The comparison for this revision is:

| Approach | Fit and limitation |
| --- | --- |
| Codex plugin / skill / MCP | [Plugin resources](../../codex-rs/plugin/src/manifest.rs) expose skills, MCP servers, apps, and hooks, but no native TUI audio-owner extension. An MCP tool can call an external service, but that service still needs a hardware-control endpoint. Model-mediated mute is unsuitable for an immediate, deterministic user control. Plugin packaging may later help discovery; it does not remove the missing seam. |
| Existing app-server API | [Realtime RPC inventory](../../codex-rs/app-server-protocol/src/protocol/common.rs) exposes start, audio/text/speech append, stop, and voice catalog, but no local microphone/speaker mute RPC. Its start/stop methods can inform the lifecycle adapter, but controlling a separately launched app-server does not control the TUI-owned voice host; stopping also cannot implement the deferred mute-only semantics. Canonical notification types can be reused without inventing another provider event format. |
| External audio proxy / system mixer / synthetic terminal keys | A proxy cannot reliably silence audio already queued at the local speaker, a system mixer affects unrelated applications, and keystroke injection cannot provide authoritative state or reliable session identity. None satisfies this contract with the existing TUI. |
| Headless Codex helper/coordinator plus narrow TUI endpoint | Selected. Coordinator, HID handling and registry stay in an optional external helper; any future native UI stays in a separate client. The initial core patch exposes existing lifecycle state/control, coordinated start admission and per-start voice selection. Persistent speaker mute and canonical-item observation are separate deferred additions. |

For Task A, expose only lifecycle start/stop, target identity/focus evidence and authoritative snapshots; persistent speaker mute and counting are deferred. Keep IPC framing/authentication and state reduction in a self-contained module with fixtures; limit edits to existing TUI code to lifecycle/owner calls and event routing. Do not redesign the main realtime backend or move audio ownership to app-server for this feature. Reuse the existing helper `AudioControls` message rather than replacing its protocol. If an upstream supported local-control API appears, replace the helper's adapter and remove the endpoint patch. Version the narrow control protocol independently of provider protocols and keep a small rebasing checklist covering only these integration points.

## Initial process placement and CLI surface

Ship an optional headless Rust helper (for example `codex-voice-coordinator`, or a separately invoked Codex subcommand). Participating TUIs launch/connect on demand to exactly one per-user coordinator through private authenticated local IPC. A lock plus process/start identity and protocol handshake prevents duplicate coordinators; stale socket files alone do not prove the prior owner is dead. The coordinator owns global HID interception, physical LED writes, stop epochs and the voice-pool lease registry. TUIs retain native audio ownership and expose only lifecycle/admission/per-start voice hooks. Do not put HID ownership in every terminal process or require a macOS UI event loop merely for menu rendering.

Configure provider-specific ordered pools and Caps enablement through configuration/CLI. Provide CLI commands or equivalent configuration for register/enroll, bind/select ON target, inspect state, start/stop, global OFF, and release Caps ownership. Explicit binding uses live instance UUID and owner identity; process exit invalidates it. Selection does not rely on window titles or a menu picker. Report pending/error/unknown states through CLI status/diagnostics as well as the physical LED; a binary LED cannot fully express uncertainty. Prompt for or explain OS permission steps without claiming the headless process bypasses TCC. Whether the chosen HID APIs require a run loop, entitlement or supported launch context is a feasibility experiment, not a reason to make the menu app mandatory.

Managed sessions must participate in coordinator start admission. If the coordinator is unavailable, refuse new managed voice starts rather than bypassing global OFF or uniqueness; existing calls keep their last actual state and are reconciled on recovery. Helper shutdown/crash must follow the lease and mapping recovery rules below; do not infer stopped audio from its own process exit. No automatic login item or always-installed system daemon is required by the initial design.

Its target picker, status, pool configuration and controls provide optional alternatives to the initial CLI surface. The richer controls and badge below are preserved for later work; do not make them prerequisites for Task A or B.

Use an AppKit `NSStatusItem` with a SwiftUI popover and no persistent Dock window. Proposed app directory: `apps/macos-voice-controls/`, including its Swift package, app bundle metadata, build script, and tests. Use system symbols, ordinary native controls, VoiceOver labels, keyboard focus, and dark/light appearance. Menu-only controls need no microphone, Accessibility, Input Monitoring, or Screen Recording access because Codex owns audio and no terminal automation is used. Optional Caps Lock interception/physical LED control has separate HID/TCC requirements: verify Input Monitoring and any Accessibility requirement for the selected API, OS and keyboard before enabling it. Do not extend the menu-only permission claim to that feature.

The status item combines a small voice icon with microphone/playback state and a numeric badge capped visually at `99+`. A tooltip and accessibility label state both mute flags in words; state is not conveyed by color alone. With multiple sessions the badge totals unread messages across reachable sessions; the popover lists each count explicitly. Disconnected/unknown is visually distinct from muted.

## Deferred independent-mute contract

This section specifies later mute controls. Task A reuses existing native start/stop and lifecycle observation without requiring a new persistent speaker-mute implementation.

The TUI owner is authoritative. Add a provider-neutral control state with `microphoneMuted`, `userSpeakerMuted`, transient interruption suppression, requested revision, applied revision, and lifecycle (`starting`, `active`, `stopping`, `inactive`, `failed`). Keep user mute state in the owning `App` session across widget parking, navigation, and reconnects. Explicitly ending and restarting voice in the same CLI instance retains the user's mute choices; a new CLI process starts with documented defaults and no silent automatic voice start.

Effective speaker suppression is `userSpeakerMuted || transientSpeakerSuppressed`. Every release/resume path must recompute that expression. Transcription and delegated tasks continue while the user speaker flag is set. Neither mute command sends a provider cancel/stop or a Codex turn interrupt.

Refactor terminal toggle handling into absolute `set_microphone_muted(bool)` and `set_user_speaker_muted(bool)` operations plus one reconciliation path. Terminal shortcuts and the companion use the same operations. Extend the existing audio session handle minimally to report completion of a controls revision or a concrete failure from the existing host acknowledgement; do not block the UI loop awaiting native device work. A superseded revision must not overwrite a later state. Preserve fail-closed behavior when a microphone privacy transition cannot be applied.

On playback mute, drop pending playback, invalidate in-flight writers, and discard arriving audio while continuing to receive transcripts. On unmute, play only newly arriving eligible audio, with no retained backlog or replay of missed answers. Unmuting mid-answer may reveal its remaining live tail; the UI should not promise a whole new answer. Device changes and reconnects must restore the effective flags before opening the audible/capture path. An acknowledgement means the host has applied its local queue/generation boundary; it cannot retract audio already submitted to OS/hardware buffers.

The Gemini integration is expected to use an external gateway that preserves the native WebRTC helper and TUI audio ownership. In that design both providers share these existing local controls; no PCM transport or provider abstraction refactor is required by this companion. Any future alternate audio path must preserve the same controls and completion contract. The companion receives opaque voice IDs/display names and capabilities from the owner; it does not implement WebRTC, PCM, Opus, provider authentication or provider event schemas. Both provider paths require independent validation; a mock or one-provider pass does not establish the other provider's behavior.

## Task A — Caps Lock lifecycle and physical LED (first)

Initial default: ON starts native voice for the explicitly selected CLI instance/thread; OFF stops native voice in **all managed local Codex sessions**. ON does not start all microphones. Global OFF does not require foreground detection. Independent mic/speaker mute remains deferred; multi-session lifecycle coordination and Task B voice allocation are in scope. Use the TUI's normal lifecycle, never key injection or executor cancellation. Stopping retires voice/audio resources; restarting creates a new voice conversation while the Codex task/thread survives. Measure setup time and context continuity per provider; do not promise an instantaneous toggle, preserved provider-side context, or universal latency figures.

| Alternative | Benefits and tradeoff |
| --- | --- |
| Native voice start/stop (recommended) | OFF ends capture/playback and releases the call; ON incurs fresh connection/context setup. Admitted Codex work continues. |
| Dual mute/unmute | Keeps voice/context warm but continues provider/session activity. Both flags need acknowledgement, and prior independent mute choices must be retained. Only as an explicitly labelled alternative mode. |
| Selected-session-only OFF | Rejected for the initial contract: it leaves other managed sessions active behind a potentially dark shared LED. Global OFF is required. |

The physical LED represents **confirmed aggregate native voice lifecycle across all managed local sessions**, independently of logical uppercase Caps Lock and microphone mute. Lit means at least one managed session is confirmed active; dark means all are confirmed stopped. Never infer OFF from key state or loss of contact. Unmanaged processes/unrelated apps are explicitly outside this contract. The coordinator uses a stop epoch/start-admission gate: OFF closes admission, invalidates pending starts, stops every active/starting owner and rechecks the registry before confirming aggregate OFF. A session discovered or started concurrently joins that barrier; an old start acknowledgement cannot reopen voice after OFF. Failed/unreachable participants keep aggregate state unknown, not confirmed silent. ON admits only the explicitly selected owner after the barrier is resolved; it never implicitly enables all microphones.
Subscribe to authoritative lifecycle transitions regardless of origin: Caps, terminal shortcut, `/voice`, provider error/disconnect, helper failure, restart and external stop all update the same state/LED reconciliation path. The pinned keymap defaults to F8 for lifecycle and F9 for mic mute; the user's F9 may be a customized lifecycle binding. Use its effective action and observed resulting state. Never toggle the LED merely because Caps/F9 was pressed, and never interpret mic mute as session OFF. Initial IPC needs start/stop acknowledgement plus ongoing lifecycle snapshots, not two independent optimistic key-state flags.

### Exact foreground-session feasibility gate

There is a promising existing source seam: `tui/src/tui/event_stream.rs` handles `FocusGained`/`FocusLost`, and `tui/src/tui.rs` stores `terminal_focused` and exposes `is_terminal_focused()`. Report those events from each authenticated CLI instance, including observation revision/time and whether actual focus reporting has been observed. The field initializes to true, so its initial value is not evidence that this is the uniquely focused terminal. A frontmost application or window title alone does not identify the exact Codex thread, terminal tab or tmux pane.

Before enabling automatic targeting, test two independent CLI instances across the supported terminal apps, windows, tabs and tmux panes, including rapid focus changes, menus stealing focus, dropped reports, startup, sleep/wake and disconnect. Accept a target only when fresh, unambiguous reports map to exactly one live instance and its explicit owner. Reject multiple/unknown/stale focus claims rather than guessing or falling back to the last window title. This inspection proves an available event surface, not reliable multi-terminal routing; no such runtime proof exists yet.

If that proof fails or the integration is disproportionate, **ON uses one explicitly selected instance/owner**. This fallback does not defer global OFF or voice allocation for other managed sessions: those rely on authenticated instance identities, not foreground windows. Process exit/PID reuse invalidates selection and requires explicit rebind. Do not silently switch a live owner or expand into terminal-specific Accessibility automation merely to avoid a session picker.

Pending, unreachable and failed states must be visible in the menu. Change the LED only after confirmation; retaining its last state is not proof of current state. Failed starts stay visibly failed, confirmed disconnects turn it off, and loss of state authority displays unknown rather than a false confirmed ON/OFF. If LED write/readback is unsupported or fails, mark the physical indicator unavailable: a dark lamp cannot then be presented as proof of silence. Menu controls remain usable. Reconcile terminal-initiated voice changes through authoritative snapshots. Serialize press transitions, suppress repeats and duplicate edges, and reject stale completions using instance/thread/call generation and operation ID.

DontSpeak's `rust/crates/ds-platform/src/macos/capskey.rs` remaps Caps to No Action and uses raw HID for physical presses; `led.rs` writes the physical Caps LED separately from logical lock state. These are source references, not universal hardware proof. Its `release_caps_key` clears the entire `UserKeyMapping` array: **do not copy that cleanup**. Preserve existing mappings; acquire exclusive Caps ownership only after conflict checks; install only the owned entry; restore/remove only that entry if it remains ours. Preserve concurrent third-party changes. Provide explicit crash/SIGKILL recovery without clearing unrelated mappings.

Treat DontSpeak/other Caps owners as conflicts: refuse concurrent ownership and require explicit handover, without overwriting their mapping or racing LED writes. Keep headless CLI controls functional without Caps ownership; the later menu client can remain usable too. Cover built-in/USB/Bluetooth and multiple keyboards, hotplug, sleep/wake, permission loss and recovery. Select exact HID APIs and confirm the proposed macOS minimum only after a focused permission/hardware experiment using the intended headless launch context. This PR installs no remap and changes no system setting.

Task A acceptance, independently of voice selection and the richer unread counter:

- [ ] Caps/lifecycle/LED controls run from the intended headless launch context with no menu app installed or running; CLI configuration and explicit ON binding suffice.
- [ ] Concurrent helper launches elect one owner; crash/restart reconciles mappings, managed calls and uncertain leases without duplicate HID/LED ownership or admission bypass.
- [ ] Permission denial/conflicting owner preserves normal Caps behavior and unrelated remaps; headless CLI controls work without the menu app.
- [ ] ON starts only the selected owner; OFF stops all managed local voice sessions while admitted coding tasks continue. Wrong/stale IDs cannot redirect ON.
- [ ] Global OFF races with simultaneous/discovered/pending starts through a coordinator gate/epoch; no late start survives the barrier.
- [ ] Foreground routing feasibility has an evidence-based outcome: verified exact mapping or explicit ON selection, without title/PID guesses; neither blocks global OFF or Task B.
- [ ] Pending starts, partial global-stop failure and unreachable owners show truthful aggregate pending/error/unknown; key presses alone never assert applied lifecycle or all-off.
- [ ] Applied lifecycle and supported physical LEDs agree after Caps, effective terminal lifecycle shortcut (including customized F9), `/voice`, errors/disconnects, helper loss, press/release/repeat, hotplug and sleep/wake. Mic mute alone does not falsely show OFF.
- [ ] Normal exit and crash recovery restore only the owned mapping and preserve concurrent remaps; DontSpeak coexistence fails safely.
- [ ] Actual startup latency, voice-context restart and hardware/OS limitations are recorded. CLI state and diagnostics are clear; richer icon/badge geometry remains deferred.

## Task B — provider-specific free-voice pool (in scope, independent of focus)

Feasible without changing the coding model or making a shared configuration race. At the pinned baseline, `tui/src/chatwidget/realtime_settings.rs` displays a voice catalog and applies selection to the next conversation; `PersistRealtimeVoiceSelection` persists shared `realtime.voice`. `tui/src/app_server_session/realtime.rs::thread_realtime_start` already accepts a per-start voice. Separate invocations can use process-local configuration overrides; reusing the persisted picker unchanged would instead let windows overwrite the shared default.

Add an in-memory instance/owner voice override through the narrow authenticated IPC: list supported voices, select an opaque voice ID for next start, and report selected versus active voice. Key it by instance UUID and explicit owner identity; retain across that owner's stop/start, discard on process exit. Leave the shared default unchanged unless the user explicitly selects a separate save-default action. A running call keeps its voice. Apply changes next start, or via explicit acknowledged stop/start; do not promise hot swapping. Task B can be tested with CLI/native start/stop and does not depend on foreground detection, Caps ownership, HID permissions or LED hardware.

Keep provider catalogs separate behind the interface. OpenAI's enum/catalog cannot validate arbitrary Gemini voice names. Separate Gemini gateway launches have their own `--voice` setting in the proposed integration, allowing distinct launch voices for terminal windows. Coordinator changes for subsequent Gemini calls need a bounded adapter metadata/call-configuration seam to advertise/validate its own IDs and accept a per-call override. Until implemented, expose the launch voice as fixed and require explicit gateway relaunch to change it; fixed launch voices alone do not satisfy Task B automatic allocation. Task B must implement and verify the per-call seam for Gemini, or explicitly report that provider as unsupported by the pool. Do not pass Gemini strings through the OpenAI enum or silently substitute voices. Model/account voice support remains live-provider validation.

Configure an ordered pool of supported voices separately for each provider. A single local coordinator allocates round-robin among **currently free** voices: scan from that pool's cursor, atomically reserve the first available ID, and advance the cursor only after a reservation succeeds. Empty/exhausted pools fail the new start with an explicit all-voices-busy/configuration error; never silently duplicate an occupied voice or cross provider catalogs.

Each lease belongs to `(instance UUID, owner ID, call generation, operation ID)`. Reserve before native startup; activate on confirmed start. Release on confirmed session end, or a failed start only after confirming it cannot produce audio. Terminal/native starts must participate in the same admission/allocation path; registering a lease after an uncontrolled start cannot guarantee uniqueness. Confirmed external stop/disconnect updates both lifecycle and lease. Loss of contact alone must not release a voice while the old session could still speak. Reconcile process/helper liveness, in-flight starts, crashed owners and coordinator restarts; uncertain leases remain unavailable until authoritative cleanup/reconciliation. Never use a timer alone as proof that a voice is free. Persist pool order/preferences separately from crash-recoverable lease identity and reconcile the live registry before admitting new allocations after coordinator recovery.

Global OFF closes start admission and invalidates the previous start epoch, stops existing and pending owners, and releases their leases only after confirmed end. Reopening admission must not resurrect invalidated operations. Explicit voice preferences are allowed only through the same free-voice reservation policy. Running conversations keep their active voice; a different selection takes effect on a later admitted start. The minimal native seam must cover start admission, terminal-start reporting, per-start voice override and end acknowledgement; the allocation algorithm and registry stay in the external coordinator.

Task B acceptance:

- [ ] Concurrent starts receive distinct currently free voices atomically in provider-specific round-robin order; occupied IDs are skipped and cursor movement is deterministic, with unchanged executor models/shared defaults.
- [ ] Failed starts, confirmed end, terminal shortcut stop, crash, disconnect and coordinator restart release/reconcile leases correctly; uncertain owners retain their reservation.
- [ ] Exhaustion refuses the new start with an explicit all-voices-busy message; no silent duplicate allocation.
- [ ] Global OFF racing with concurrent starts stops all owners and prevents stale leases/start acknowledgements from reviving voice.
- [ ] Selection, active voice and next-start voice remain owner-scoped through stop/start, navigation and PID reuse.
- [ ] Active-call selection waits for next start or explicit restart; no unsupported hot-swap claim.
- [ ] Invalid/unavailable provider voice is reported; OpenAI and Gemini IDs/catalogs never cross accidentally.
- [ ] Gemini per-call allocation works through the explicit adapter capability; separate launch voices alone are not an allocation pass. Missing capability/provider access is reported explicitly.
- [ ] Source/config proof is distinguished from actual audible voice differentiation and provider access.

## Narrow local integration

Add an opt-in `tui.voice_controls.enabled` setting and a small macOS-only listener owned by each TUI process, proposed module `codex-rs/tui/src/voice_control_service.rs`. It sends typed requests into the existing `AppEvent` queue and receives immutable state snapshots. It cannot execute commands, approve tools, read arbitrary files, start coding tasks, or send arbitrary app-server methods. The headless coordinator and future menu client do not connect directly to the voice-host child pipe or become a second audio owner.

Use a versioned, length-prefixed JSON protocol over a per-instance Unix domain socket. The helper pipe's same-build protocol is separate and must not be treated as the public companion contract. Proposed client operations:

- `hello`: authenticate, negotiate protocol version/capabilities, return initial snapshot.
- `subscribe`: stream revisioned snapshots and liveness; after a gap, fetch a full snapshot.
- Task A: `startVoice` / `stopVoice` for explicit instance/owner with expected generation/revision, coordinator epoch and idempotent operation ID. Global OFF fans out to all managed owners behind a start-admission barrier. Lifecycle snapshots include terminal controls/failures. Starting voice does not start a coding task; optional focus evidence only selects ON targets.
- Task B: start admission/reservation and end acknowledgements plus `listVoices` / `selectVoiceForNextStart` with owner-scoped opaque voice ID and capability validation; report active and selected voice separately.
- Deferred independent controls: `setMicrophoneMuted` / `setSpeakerMuted`: instance ID, owner thread ID, call generation, expected revision, request ID, and absolute boolean. Validate the target again on the TUI event loop. Stale revisions return a conflict with current state; never blindly retry an unmute after a conflict.
- Deferred counter: `acknowledgeMessages`: an explicit per-session high-water sequence from a snapshot; messages arriving later stay unread.

Initial snapshots need identity, lifecycle, operation/epoch acknowledgement, liveness, effective lifecycle shortcut, voice allocation/lease state and optional focus evidence. Independent mute and unread-count fields below are deferred capabilities. Snapshot fields include instance UUID, protocol/build versions, voice owner thread ID, call generation, connection phase, start/stop capabilities, provider-supplied voice catalog and active/next-start selection, mute intentions and applied state, effective output suppression, work status, unread count, last message sequence, effective shortcut text, and sanitized error code. No audio, SDP, provider credential, transcript text, tool arguments, or filesystem content crosses this socket. The service uses bounded frames (initial proposal 64 KiB), bounded clients/queues, authentication timeout, and heartbeat/EOF handling. Slow subscribers are disconnected and must resnapshot; they cannot block audio controls.

Discovery uses a dedicated per-user runtime directory, not the repository. Use a short private socket path to respect macOS Unix socket path limits, with an atomically published descriptor in a 0700 directory and 0600 descriptor/socket. Each descriptor contains a random instance UUID, socket location, protocol version, process start identity, and a cryptographically random per-process capability token. The token is never in process arguments, environment diagnostics, telemetry, or logs. Use no-follow/ownership checks on discovery files and verify peer UID; reject replaced/symlinked or foreign-owned paths. Only the owning process removes its own descriptor/socket. Reuse or extract the existing guarded Unix socket helpers after checking their suitability instead of copying unchecked filesystem code.

This authorizes a local same-user control client/coordinator, not a defense against arbitrary malicious code already running as that user. It must not reuse OpenAI/Gemini login tokens. No TCP port is opened. Shipping sandboxed/App Store distribution would need a separately reviewed IPC/entitlement design; the first build is a local, unprivileged headless helper. The future app is a separate consumer and distribution decision.

On normal CLI exit remove discovery state; on crash the coordinator marks the session unavailable after EOF/liveness expiry and disables controls. A newly started process always has a new instance UUID and token, even when a PID is reused. A coordinator restart reconciles authoritative lifecycle and lease state from still-running TUIs before admitting starts. A later menu-client restart obtains snapshots from the service. After a TUI restart, counters begin anew and old descriptors never restore mute or unread state into a different session. During provider reconnect, keep the same owner session and mute intentions, advance call generation, and apply flags before audio begins. During loss of the coordinator connection, Codex retains its actual applied state, refuses new managed starts and reports loss of coordination; recovery reconciles rather than reallocating uncertain voices.

## Deferred unread-counter research

The first version counts **completed assistant voice transcript entries**, not model tokens, audio packets, partial captions, every executor update, or guaranteed unheard sentences. One canonical nonempty assistant `TranscriptSegment` item contributes at most one entry, keyed by `(realtimeSessionId, itemId)`. This matches available stable events and keeps the product label `new voice messages while muted` honest. A provider can split a response into multiple transcript entries; the UI must not describe the number as tasks or complete answers.

Observe item start/completion at the TUI event routing boundary even when the voice-owning widget is parked. Mark active assistant items when user playback mute becomes applied, and mark new items while it is applied; increment only when such an item completes with meaningful text. A completion without a prior start is eligible only if it arrives live while muted. Distinguish live notifications from history hydration/replay, keep canonical-ID deduplication, and do not count temporary barge-in suppression as user mute. Do not infer acoustic audibility from completion timing.

Exclude user transcripts, whitespace-only items, duplicate completion notifications, historical replay, and `BemItemPromoted`/underlying executor messages already represented by voice. Interrupted partials without a completed item do not increment. Codex work progress remains a separate status (`running`, `waiting for approval`, `idle`, `unknown`), not a second message source. Final text-only work results remain visible in the terminal; expanding the badge to those results requires an explicit cross-source identity contract to avoid double-counting.

Maintain a per-owner journal of sequence numbers and deduplication metadata in the TUI, with an explicit finite retention budget and saturation behavior. Suggested limits: 4,096 recent completed IDs per live session and a saturating count; if a recoverable event gap cannot be reconciled, expose `countUnavailable` instead of inventing an exact number. Do not silently evict IDs while continuing to accept replay from their range. Reconnect must resume from a cursor or resynchronize a snapshot without counting history again. `Mark as read` advances the acknowledged sequence only to the displayed high-water mark. Counts survive companion restarts and speaker unmute, but not TUI process restart. No transcript text needs to be retained by the companion.

Stopping voice or switching its owner retains the previous owner's unread journal as an inactive, read-only entry in the same TUI instance. A new owner receives a separate journal; counts never migrate between owners. Retire an old journal only after explicit acknowledgement/removal, process exit, or a visible retention-limit outcome that marks its count unavailable. `acknowledgeMessages` must validate the instance UUID, original owner ID and displayed sequence high-water mark; it cannot acknowledge the current owner by default when the request names an older one. Inactive entries expose read acknowledgement but no audio controls.
