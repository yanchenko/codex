# Headless Codex voice controls

Status: implementation authorized; this document must receive independent plan review before coding. Codex source baseline: `4bc83aa5f7ebfec8492bb5747affe0fc8433fcad`. No implementation or hardware/provider acceptance is established by this plan.

## Initial deliverables

Extend the Codex CLI codebase with an optional headless coordinator and narrow native voice integration. No top bar, menu app, AppKit, SwiftUI, separate GUI, independent speaker-mute feature, unread counter or artwork is required. Earlier research is isolated in [deferred menu notes](macos-voice-menu-deferred.md).

1. **First priority: automatic voice acquisition/release.** A configurable ordered pool for each provider allocates a currently free voice round-robin on every new managed voice session. Simultaneous sessions cannot share an occupied voice. Exhaustion refuses a new start explicitly. Allocation is independent of foreground-window detection and Caps hardware availability.
2. **Second priority: global Caps silence through native stop.** ON starts actual native voice in an explicitly selected/bound Codex instance and owner. OFF stops native voice in **all managed local Codex sessions**, including pending starts. Admitted coding tasks continue. The physical LED follows confirmed aggregate voice lifecycle, regardless of whether a change originated from Caps, the terminal or a failure.

ON never implicitly enables all microphones. Stopping voice releases the voice call/audio resources; restarting creates a fresh voice conversation while the coding thread/task survives. Record startup/context behavior per provider without promising instantaneous restart or preserved provider-side conversation state.

## Independent platform API decision gate

Primary-source review performed 2026-10-10; source documentation is evidence for API contracts, not permission or physical hardware acceptance. This gate precedes selecting/implementing hardware adapters; coordinator work can proceed independently.

| Approach | Primary evidence and decision |
| --- | --- |
| macOS raw IOHID plus owned remap and direct output element | Apple documents [keyboard remapping via hidutil/IOHIDEventSystemClient](https://developer.apple.com/library/archive/technotes/tn2450/) and [IOHIDDeviceSetValue](https://developer.apple.com/documentation/iokit/1588651-iohiddevicesetvalue). The latter returns an IOReturn and waits until an output/feature report is issued: check errors on a dedicated worker; this is not optical LED proof. Recommended first implementation candidate because physical edges and indicator writes remain independent of logical uppercase state. Acquire only after access/monitor readiness; remap is an owned read/merge/write transaction with conflict detection and recovery. Apple's remapping note is old: its no-special-privileges statement is not a blanket current TCC exemption. It also says mappings apply across users and disappear when services/restart remove them; inspect actual matching scope and re-enumerate on hotplug. |
| macOS CGEventTap alternative | Apple's [security session](https://developer.apple.com/videos/play/wwdc2019/701/) distinguishes Input Monitoring for listen-only from Accessibility for a modifying tap. [Tap creation](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:)) is fallible and needs a run-loop source; [tap types](https://developer.apple.com/documentation/coregraphics/cgeventtype) include disabled-by-timeout/user-input. Passive observation cannot suppress the native Caps action. Active filtering avoids a persistent remap but requires a safe permission/re-enable path and experimental proof that filtering Caps prevents logical toggles for supported keyboards. Official API docs do not establish that last claim; do not accept DontSpeak's contrary comment as proof either. Keep this as the comparison spike if raw HID suppression fails, not an automatic fallback requesting broader permission. |
| Windows hook versus raw input | Microsoft [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc) documents suppression, a dedicated message loop and silent removal on callback timeout; it recommends raw input for observation. Raw input observation alone does not implement suppression. A bounded hook callback that only queues Caps edges is the appropriate suppression candidate; never block it on coordinator IPC. [Indicator IOCTL](https://learn.microsoft.com/en-us/windows/win32/api/ntddkbd/ni-ntddkbd-ioctl_keyboard_set_indicators) sets keyboard indicators, but does not establish universal unprivileged class-device access or visible success. Query/preserve other indicators, report actual access/write errors and test reconnect. Do not use synthetic Caps toggles to drive a lifecycle LED because that couples uppercase state. |
| Linux evdev/XKB versus compositor shortcut | The [kernel input protocol](https://docs.kernel.org/input/event-codes.html) provides physical EV_KEY state, repeat values, SYN_DROPPED resynchronization and EV_LED output/query. Use capability checks and current-state recovery after loss; access to input nodes is an environment prerequisite, not permission to install broad group/udev changes. XKB remapping is desktop-owned; [setxkbmap](https://manpages.ubuntu.com/manpages/noble/man1/setxkbmap.1.html) explicitly does not support changing Xwayland's keymap. Prefer compositor-supported configuration over rewriting desktop stores. The [GlobalShortcuts portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html) offers session-bound activation/deactivation and user-approved bindings. It is a safer shortcut alternative when supported, but does not promise bare Caps suppression or physical LED control; expose those as separate capabilities. No generic Wayland fail-open adapter. |

### macOS first-run, revocation and binary identity

Provide explicit `caps setup/status/disable` or equivalent CLI operations. Startup of ordinary voice allocation must not trigger a keyboard permission prompt. On explicit setup, explain the exact access required, preflight via the documented IOHID listen-event access check and request only that access if undetermined. Apple's [Input Monitoring settings instructions](https://support.apple.com/guide/mac-help/mchl4cedafb6/mac) are the recovery path after denial; do not repeat prompt attempts or modify the privacy database. Accessibility is conditional on an actual modifying/posting approach, not requested just in case. Never require Full Disk Access for this feature.

Use a stable native helper installation path and code-signing identity for distribution; development/rebuilt binaries need an explicit reauthorization diagnostic. Apple DTS describes [stable signing and responsible-code attribution](https://developer.apple.com/forums/thread/678819) for TCC; that article concerns filesystem protection, so applying it to the keyboard helper is a design precaution, not proof of exact Input Monitoring attribution. Test whether the actual launch chain attributes consent to the helper or terminal, including restart/update, before promising persistence. Do not daemonize or rotate temporary executable paths blindly. A native headless executable can have a run loop without introducing a menu app.

On denial/revocation/open failure, disable Caps acquisition, preserve/restore only owned mappings and keep allocation/CLI global OFF available. On permission recovery reopen/re-enumerate, verify readiness, then reacquire explicitly; do not treat an old boolean grant as durable. On sleep/wake/hotplug revalidate devices, mapping ownership and LED capability, then reconcile from authoritative native voice snapshots. No unrelated key logging. Permission grant is distinct from monitor readiness, suppression readiness and indicator-write acknowledgement.

Required adapter evidence: API/build check; mock permission/ownership/error tests; safe dedicated-machine or VM checks for first denial, later grant, revoke while enabled, update/relaunch identity, logical Caps neutrality, physical LED and non-Caps indicator preservation, multi-keyboard/hotplug/sleep recovery and external voice lifecycle changes. A VM can validate permission flow but may not expose a physical LED. Current research executed no permission prompt, remap or hardware test, so all such acceptance remains unverified. If safe hardware proof requires the user's active session/permissions, report that exact prerequisite; do not silently choose a destructive experiment.

## Process and local protocol

Use one optional on-demand Rust coordinator binary or Codex subcommand per user. Participating TUIs register/connect through private authenticated local IPC. No login item, privileged daemon or GUI is required. A singleton lock, process/start identity and protocol handshake prevent two coordinator owners; stale files alone do not prove a prior process dead. The coordinator owns HID/LED, admission epochs, pool cursors and lease registry. Each TUI owns its normal audio helper and provider session.

Expose CLI/configuration for enablement, pool definitions, enroll/register, explicit bind/select ON target, inspect status, start, per-owner stop, global OFF, and release Caps ownership. Default to explicit target selection using live UUID/owner, not window title/PID alone. Process exit invalidates binding. Optional automatic focus routing requires fresh unique per-instance observed focus events, tested across terminals/tabs/tmux, startup, menus, sleep and dropped reports. Ambiguity rejects targeting; failure of this experiment does not block explicit binding or allocation.

Use a versioned bounded protocol over private Unix sockets on macOS/Linux and a local named pipe on Windows with explicit current-user access control and remote-client rejection. Reuse repository platform transport primitives where suitable; verify ACL/peer identity behavior with negative tests. A pipe name alone is not authentication. Proposed integration points: isolated protocol/coordinator crates or modules, CLI subcommand wiring, a small TUI service/event adapter, config/schema and tests. Proposed initial frames are at most 64 KiB, with bounded clients/queues and authentication timeout. Discovery descriptors live in a private 0700 per-user runtime directory, with 0600 sockets/files, random instance UUID, process-start identity and per-instance random capability token. Validate ownership, no-follow paths and peer UID. Do not log tokens. This is a same-user trust boundary, not protection against arbitrary malicious code under the same user.

Operations include handshake/capabilities, registration, subscription/full snapshot, start admission/reservation, startVoice, stopVoice, confirmed end, global OFF and status/binding/pool configuration. All mutations carry owner, generation, operation ID, expected revision and admission epoch where applicable. Reject stale targets; duplicate operation IDs are idempotent. Slow subscribers reconnect and resnapshot without blocking voice control. Snapshots report lifecycle, actual active voice, pending reservation, revision/epoch, liveness and sanitized error; no audio, SDP, transcripts, coding commands, approvals or provider credentials cross this control interface.

Admission runs asynchronously: the TUI dispatches a request and receives a typed result event tagged with start attempt, owner, generation and epoch; it never blocks the event loop waiting for a response that needs that loop. Revalidate tags before applying a grant. Cancelling/resetting a start future is not proof its worker or helper has retired: require an explicit pending-worker retirement acknowledgement before releasing that reservation. The baseline `realtime-webrtc/src/session.rs::close()` aborts its actor; that alone is not a child-process exit acknowledgement. Add a narrow retirement signal backed by actual helper process wait/reaper completion, surviving startup cancellation and actor teardown. Lease release and global-stop completion must await that signal, not merely widget reset, actor completion or provider disconnect. Test actual helper exit before release. Keep state reduction and wire validation independently testable. Enabling managed mode while a voice call already exists must register/reserve its actual voice or refuse enrollment until it stops; never silently double-allocate or interrupt an existing call merely to enroll.

## Admission, global OFF and leases

Every managed start path, including terminal shortcuts and `/voice`, must pass coordinator admission **before** creating a provider call/audio. Each reservation identifies `(instance UUID, owner ID, call generation, operation ID)` and the provider/voice. Scan the configured provider pool from its cursor for the first free supported voice, reserve atomically, then advance the cursor. Explicit preferences also obey free-voice reservation. Empty/invalid/exhausted pools fail with a useful message; never duplicate or cross provider catalogs.

Activate a lease only after confirmed start. Release only after confirmed voice end/local audio retirement, or failed startup known incapable of producing audio. Provider disconnect alone is insufficient if native playback might remain. Loss of contact, process/child uncertainty or timeout retains an unavailable lease until reconciliation proves cleanup. Do not infer safety from PID reuse or a timer. Persist crash-recoverable lease identity durably before returning a grant; keep pool configuration/cursor consistent with that reservation. After restart quarantine all persisted occupied leases until generation-identical TUI/helper evidence confirms actual retirement or proves the call still active. Reconcile surviving TUIs/helpers before new admissions; journal corruption or uncertain durability fails admission rather than silently starting with an empty pool.

Global OFF closes admission, advances a stop epoch, invalidates previous pending starts and stops all active/starting managed owners. During the barrier accept new registrations only in a confirmed stopped state; an existing active/uncertain registrant joins reconciliation and keeps the barrier unresolved. Recheck registry until every admitted participant, including concurrent registrations, has confirmed stopped. Old start acknowledgements cannot revive a stopped epoch. Reject new starts while stopping; after successful global OFF, a later explicit start/ON can open a fresh epoch. Unreachable participants keep state unknown and block a false all-off claim. Already admitted Codex coding work is untouched.

Coordinator loss refuses new managed starts. Existing calls retain actual state and reservations until recovery; a replacement coordinator cannot reallocate uncertain voices. Define normal shutdown to stop/reconcile managed calls before releasing ownership, or return a clear incomplete/unknown result if that cannot be confirmed. Never claim its own process exit proves all voice stopped. Unmanaged processes/unrelated applications are outside global OFF; expose enrollment clearly.

## Caps ownership and LED truth

One physical key-down edge requests a toggle based on coordinator lifecycle, not logical Caps state; ignore repeats and release-only edges. If any voice is active or starting, request global OFF. From confirmed all-off, request ON for the bound owner. Unknown state permits stop/reconcile, never blind ON. Rapid presses are serialized into the same epoch/revision reducer.

The LED reflects confirmed aggregate native lifecycle: lit when at least one managed voice is confirmed active, dark only when all are confirmed stopped. Pending/unknown/errors are explicit in CLI status. A binary LED cannot encode all states: retain last confirmed indication while unknown and expose indicator-unavailable if writes cannot be confirmed; never market dark hardware as a universal proof of silence. Reconcile after every lifecycle origin, including effective F-key binding, `/voice`, provider failure, helper failure, external stop and recovery. Mic mute alone does not extinguish an active-session indicator.

Acquire Caps only after permission/capability/conflict checks and suppression readiness. DontSpeak/other ownership is an explicit conflict, not something to overwrite. On macOS read/merge only the owned remapping entry, preserve every unrelated mapping, and restore/remove only if it is still ours. Keep a recovery record for hard crashes; preserve concurrent third-party changes and never clear all `UserKeyMapping`. No global remap or interruption of the user's running voice is allowed merely to execute automated tests.

LED writes need applied/error reporting rather than DontSpeak's best-effort void API. Inspect the actual HID result/readback capabilities; when physical confirmation is unavailable, report the limitation rather than inventing it. Cover keyboard attach/detach, permission loss, sleep/wake, multiple devices, normal release and crash recovery. Use pure/mock platform tests by default. Actual physical QA requires a safe dedicated session and records unavailable hardware/permission cases.

## Provider voice integration

OpenAI already accepts a per-start voice; use its supported catalog without changing the coding model or shared persistent preference. A running call retains its allocated voice. Changes apply on next admitted start, not hot swap.

Gemini gateway currently has a launch-level `--voice`; different fixed launch values alone do not implement automatic allocation. Add a narrow bounded capability/per-call voice configuration seam after integrating the independently reviewed gateway branch. Until it exists, report Gemini allocation as a specifically blocked deliverable, not silently excluded or complete. Do not pass arbitrary Gemini voice IDs through the OpenAI enum. Keep provider-specific validation, model/account capability and errors explicit. Provider credentials remain with the original provider client/gateway, never with the coordinator. Actual audible differentiation requires real-provider QA; mocks prove routing and uniqueness only.
